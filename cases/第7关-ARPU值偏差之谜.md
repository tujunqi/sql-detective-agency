## 一、【案情通报】

浪潮视频是一个内容平台，收入有三条线：**VIP 会员订阅**（30 元/月卡）、**单片付费**（6 元/部）、**直播打赏**（金额不定）。

三个数字的出处：

- **报表 A（数据组）**：9 月 ARPU = 8 元——"全量活跃用户口径，行业通用算法，没错。"
- **报表 B（商业化组）**：9 月 ARPU = 15 元——"我们按 VIP 收入算的，这是核心收入，没错。"
- **竞对财报**：ARPU 30 元——"上市公司财报，总不会错吧？"

王总的困惑很实在："如果 8 元是对的，我们和竞对差 4 倍，董事会要问战略是不是错了；如果 15 元是对的，为什么数据组不认？**先告诉我，这三个数到底谁是谁？**"

**任务目标**：算出 9 月真正的 ARPU，解释三个数字各自的来路，并说清楚 ARPU 与 ARPPU 的关系——让王总明天在董事会上能一句话讲明白。

## 二、【指标卷宗】ARPU 与 ARPPU：一对常被认错的兄弟

### 口径 A：ARPU（Average Revenue Per User，每用户平均收入）

- **计算逻辑**：`统计周期总收入 ÷ 全量活跃用户数`。内容平台的分母通常 = 去重活跃键（注册用户按账号 + 游客按设备，即 `COALESCE` 口径）。
- **适用场景**：衡量整个平台的变现效率，是投资人和竞对分析的标准指标。
- **歧义坑点**：**收入包含哪些**（会员 + 单点 + 打赏 + 广告？）与**分母包含哪些**（游客算不算）必须成对说明——每一样都能让数字差一半。

### 口径 B：ARPPU（Average Revenue Per Paying User，每付费用户平均收入）

- **计算逻辑**：`统计周期总收入 ÷ 付费用户数`。
- **适用场景**：衡量付费用户的付费深度，运营调价、会员权益设计常用。
- **歧义坑点**：分母从"全量活跃"换成"付费用户"，数字会翻几倍——**把 ARPPU 当 ARPU 汇报，是行业级经典事故**。付费率越低，两个数差距越大。

### 口径 C：分收入线 ARPU（拆分口径）

- **计算逻辑**：按收入类型拆开各算：会员 ARPU、广告 ARPU、打赏 ARPU。
- **适用场景**：收入结构分析，判断增长引擎在哪条线。
- **歧义坑点**：拆分口径只算单一收入线的"ARPU"**不是 ARPU**，是"该收入线的人均贡献"——单拿一条线的数当 ARPU，必然偏低（本案报表 A 的病根之一）。

### 行业差异速记

| 行业 | ARPU 分母习惯 | 收入口径习惯 |
|---|---|---|
| 内容平台 | 全量活跃（含游客），按设备 + 账号去重 | 会员 + 单点 + 打赏 + 广告，须注明是否含广告 |
| 电商 | 通常改谈 ARPU 的兄弟指标：月均消费额 / 客单体系 | 支付 GMV 口径，剔除未支付 |
| 在线教育 | 分母用正式学员，试听用户单列 | 学费实收，延期退费要回冲 |

### 面试标准回答话术

> "ARPU = 周期总收入 ÷ 全量活跃用户，ARPPU = 周期总收入 ÷ 付费用户数，两者关系是 **ARPU = ARPPU × 付费率**。汇报时我先钉收入口径（含哪些收入线、含不含广告）和分母口径（游客算不算、按账号还是设备去重），再和竞对比——**竞对财报的 ARPU 也要先看它的口径脚注**，口径不一致的比较没有意义。"

### 新手最容易踩的错误统计方式

1. **分母错用付费用户**：拿 ARPU 的公式套付费分母，算出的是 ARPPU 还不自知。
2. **收入只算一条线**：只算 VIP 或只算广告，"人均贡献"冒充"ARPU"。
3. **分母漏游客**：`COUNT(DISTINCT user_id)` 静默忽略 NULL，游客占比高的平台 ARPU 被系统性抬高。

## 四、【探案任务】

> ⏱️ **限时挑战**：第 2 步建议计时 **5 分钟**完成"限时解码"。

### 第 1 步 · 口径对齐

要回答王总"我们变现效率到底怎么样"，ARPU 应该怎么算？

- A. VIP 订阅收入 ÷ 付费用户数（报表 B 的算法）
- B. 9 月全部收入（会员 + 单点 + 打赏）÷ 全量活跃用户（注册按账号 + 游客按设备）
- C. 全部收入 ÷ 收入流水里出现过的用户数

<details>
<summary>点击核对答案</summary>

**选 B**。ARPU 的分子是**全部收入线**，分母是**全量活跃用户**（含游客）。A 是双错口径（只算一条收入线 + 分母用付费用户），C 的分母"收入流水里的用户数"其实就是付费用户数——算出来的是 ARPPU。三个数各归各位后你会发现：**8 元才是真正的 ARPU，它不难看。**

</details>

### 第 2 步 · 基础核算（限时 5 分钟）

写出 9 月的正确 ARPU：总收入 976 元级别的分子 + 去重活跃键的分母，保留 1 位小数。

<details>
<summary>卡住了？点击看提示</summary>

分子：`SUM(amount)` 不筛 income_type；分母：`COUNT(DISTINCT COALESCE(user_id, device_id))`（游客按设备兜底）。两个子查询相除，`ROUND(..., 1)`。

</details>

### 第 3 步 · 真相追踪

三个数字各是什么来路？写 SQL：① 按 `income_type` 拆收入结构（VIP 占比多少）；② 分母对照——全量活跃去重键数 vs 只数注册用户 vs 付费用户数；③ 复现报表 A、报表 B 的算法，逐个对号入座。

## 五、【真相大白】

### 5.1 异常根因拆解

**真正的 ARPU 是 8.0 元**（总收入 976 ÷ 活跃 122 人），三个数字全部验明正身：

1. **报表 A 的 8 元 = 正确的 ARPU**。数据组没算错，只是没人给这个数"验明正身"。它难看的观感来自错误的比较对象——拿它直接对标竞对财报的 30 元。
2. **报表 B 的 15 元 = 双重口径错位**。分子只算 VIP 订阅收入（600 元，漏了单点 120 + 打赏 256，收入少算 39%），分母却是全部付费用户（40 人）。600 ÷ 40 = 15——它既不是 ARPU 也不是 ARPPU，是"VIP 收线的户均贡献"，一个不该存在的指标。
3. **竞对的 30 元 = 大概率是 ARPPU 口径**。上市公司财报的"ARPU"脚注常写明分母是付费用户（或含广告收入）。我们自己的 ARPPU = 976 ÷ 40 = **24.4 元**，和 30 元同一个量级——真正该带进董事会对比的是它。**恒等式验证：ARPU = ARPPU × 付费率 = 24.4 × (40/122) = 8.0**，三个数被一条公式串成一条线。

### 5.2 参考答案 SQL（逐行注释）

```sql
USE case07_arpu;

-- 【第2步 · 正确 ARPU：全部收入 ÷ 全量活跃用户】
SELECT
  ROUND((SELECT SUM(amount) FROM user_income_log
          WHERE income_time < '2026-10-01'), 2)          AS total_income,  -- 976.00（三条收入线全算）
  (SELECT COUNT(DISTINCT COALESCE(user_id, device_id))
     FROM user_active_log WHERE active_time < '2026-10-01') AS active_users, -- 122（含游客）
  ROUND((SELECT SUM(amount) FROM user_income_log
          WHERE income_time < '2026-10-01') /
        (SELECT COUNT(DISTINCT COALESCE(user_id, device_id))
           FROM user_active_log WHERE active_time < '2026-10-01'), 1) AS arpu_correct -- 8.0
FROM DUAL;

-- 【第3步-① · 收入结构：VIP 只占 61%】
SELECT
  income_type,
  SUM(amount)             AS total,    -- 收入线金额
  COUNT(DISTINCT user_id) AS users,    -- 该线付费人数
  COUNT(*)                AS txns      -- 流水笔数
FROM user_income_log
GROUP BY income_type;
-- 结果：vip_subscribe 600/20人/20笔；single_pay 120/10人/20笔；reward 256/10人/10笔
-- VIP 占 600/976 = 61%——漏掉另外 39%，报表 A 的分子就瘸了

-- 【第3步-② · 分母对照：122 vs 100 vs 40】
SELECT
  COUNT(DISTINCT COALESCE(user_id, device_id)) AS active_all,        -- 122（ARPU 的分母）
  COUNT(DISTINCT user_id)                      AS active_registered, -- 100（漏 22 个游客）
  SUM(user_id IS NULL)                         AS guest_cnt          -- 22 个游客
FROM user_active_log;

-- 【第3步-③ · ARPPU 与恒等式验证】
SELECT
  ROUND((SELECT SUM(amount) FROM user_income_log) /
        (SELECT COUNT(DISTINCT user_id) FROM user_income_log), 1) AS arppu,       -- 24.4
  ROUND((SELECT COUNT(DISTINCT user_id) FROM user_income_log) /
        (SELECT COUNT(DISTINCT COALESCE(user_id, device_id)) FROM user_active_log) * 100, 1) AS pay_rate_pct, -- 32.8
  ROUND( (SELECT SUM(amount) FROM user_income_log) /
         (SELECT COUNT(DISTINCT user_id) FROM user_income_log) *
         (SELECT COUNT(DISTINCT user_id) FROM user_income_log) /
         (SELECT COUNT(DISTINCT COALESCE(user_id, device_id)) FROM user_active_log), 1) AS arpu_check -- 8.0
FROM DUAL;
-- 恒等式：ARPU = ARPPU × 付费率 = 24.4 × 32.8% ≈ 8.0 ✓

-- 【错法复现 · 报表A：只算 VIP 收入】
SELECT ROUND((SELECT SUM(amount) FROM user_income_log WHERE income_type = 'vip_subscribe') /
       (SELECT COUNT(DISTINCT COALESCE(user_id, device_id)) FROM user_active_log), 1) AS arpu_report_a; -- 4.9

-- 【错法复现 · 报表B：VIP 收入 ÷ 付费用户（双重错位）】
SELECT ROUND((SELECT SUM(amount) FROM user_income_log WHERE income_type = 'vip_subscribe') /
       (SELECT COUNT(DISTINCT user_id) FROM user_income_log), 1) AS arpu_report_b; -- 15.0
```

### 5.3 错误写法对比

**错误写法一：分母错用付费用户（ARPPU 冒充 ARPU）**

```sql
SELECT ROUND(SUM(amount) / COUNT(DISTINCT user_id), 1) AS arpu  -- 错：这是 ARPPU
FROM user_income_log;
```

错在哪：976 ÷ 40 = **24.4**。公式没错、SQL 没错，但名字错了——这是 ARPPU，比真 ARPU 高 3 倍。如果拿它去对标竞对的 ARPU，董事会会得出"我们变现效率很高"的错觉；付费率越低，虚高越离谱。

**错误写法二：收入只算一条线**

```sql
SELECT ROUND(SUM(CASE WHEN income_type = 'vip_subscribe' THEN amount ELSE 0 END)
       / (SELECT COUNT(DISTINCT COALESCE(user_id, device_id)) FROM user_active_log), 1) AS arpu
FROM user_income_log;
```

错在哪：600 ÷ 122 = **4.9**，比真实 ARPU 低 3.1 元（-39%）。单收入线的"人均贡献"有它的分析价值，但不能叫 ARPU——收入口径缺哪条线，数字就瘸哪条腿。

## 六、【侦探办案笔记】

### 本关指标口径总结

- **ARPU = 总收入 ÷ 全量活跃**（含游客，`COALESCE` 去重）；**ARPPU = 总收入 ÷ 付费用户**；恒等式 `ARPU = ARPPU × 付费率` 可用于验算。
- 收入口径先列清单（会员/单点/打赏/广告），少一条线数字就偏低；分收入线的"人均贡献"不要叫 ARPU。
- 和竞对财报比 ARPU 之前，先读它的口径脚注——上市公司的"ARPU"经常是 ARPPU 或含广告的口径。
- 付费率 32.8% 的平台，ARPU 和 ARPPU 差 3 倍是正常现象，不是数据事故。

### 业务方对齐口径的标准提问话术

1. "这个 ARPU 的**收入包含哪几条线**？含不含广告？"
2. "**分母是全量活跃还是付费用户**？游客算不算？"
3. "和竞对比的时候，**对方财报的口径脚注**写的是什么？"

### 同类异常排查的通用方法论

"一个指标三个数"类案件（董事会级）三步走：

1. **给每个数验明正身**：把三份 SQL 的分子分母各翻译成一句话，贴上正确指标名；
2. **找恒等式串联**：ARPU = ARPPU × 付费率、GMV = 客单价 × 订单数——恒等式能把吵架的三方拉到同一条公式上；
3. **输出对比矩阵**：我方 ARPU 8.0 / ARPPU 24.4 / 付费率 32.8%，竞对口径逐项对齐后再比大小。
