## 一、【案情通报】

深夜食记是一个美食内容社区，用户白天收藏菜谱，深夜流量最高。9 月 19 日产品上线了新改版，9 月 21 日上午，增长运营阿花照例拉日报，看到 9-20 批次的新增用户次日留存时手一凉：

> "**25%**。9-20 新增了 20 个用户，到 9-21 只有 5 个回来。历史基线一直是 45% 上下。改版是不是把新用户吓跑了？老板两点钟要听结论，回滚方案都写好了。"

她顿了顿又补充："不过有个细节我很在意——有个用户半夜十二点私信我，说'**第二天又来刷了两小时菜谱**'，可他不在回访名单里。而且隔壁报表组的'全量用户次日留存'显示 62.5%，涨了。一个跌一个涨，总有一份在撒谎。"

**任务目标**：还原 9-20 批次的真实次日留存，判定"缩水"是真是假；如果是假的，找出那 20 个百分点去哪了。

## 二、【指标卷宗】次日留存率：一个公式，三处暗门

**次日留存率** = 某日新增（或活跃）用户中，在**次日**再次活跃的比例。公式只有一行，暗门有三处。

### 口径 A：新增用户次日留存（本案主角）

- **计算逻辑**：分母 = 当日**新增**（注册）用户；分子 = 其中在次日再次活跃的人。
- **适用场景**：衡量拉新质量与新手引导效果——买来的量留不留得住。
- **歧义坑点**：分母是"当日全部新增"，不是"当日活跃的新用户"；分子要定"活跃"含哪些行为（登录？浏览算不算）。

### 口径 B：全量用户次日留存

- **计算逻辑**：分母 = 当日所有活跃用户（老用户 + 新用户）；分子 = 次日再活跃的人。
- **适用场景**：衡量产品整体粘性。
- **歧义坑点**：老用户基线高，这个数字**天然比新增留存高一大截**。拿它和新增留存的历史曲线比，属于自欺欺人。

### 口径 C：次日/7日/N日留存族

- **计算逻辑**：同一套公式换时间窗：7 日留存、30 日留存。
- **适用场景**：不同业务看不同窗口——电商看 7 日，教育看 7/30 日，工具看次日。
- **歧义坑点**：**时间窗口没关**是最常见的翻车点——统计"次日"时把次日之后的数据也捞了进来（晚到的回访被算成次日留存），数字悄悄变高；反过来，**在次日还没结束时看报表**，数字又天然偏低。

### 行业差异速记

| 行业 | 惯用窗口 | 特殊之处 |
|---|---|---|
| 内容社区 | 次日 + 7 日，含免登录浏览 | 游客可消费内容，"活跃"必须定义是否含浏览 |
| 电商 | 7 日/30 日复访 | 次日留存低是常态，购买周期长 |
| 在线教育 | 次日 + 7 日（开课后） | 以"到课"为活跃，试听用户与正式学员分开算 |

### 面试标准回答话术

> "次日留存我会先钉死四个要素：**分母人群**（新增还是全量）、**分子的活跃定义**（哪些行为、免登录算不算）、**时间窗口**（严格次日 0 点到 24 点，还是滚动 24 小时）、**数据完备性**（报表生成时间点之后的数据还没进来）。四件事差一件，同一个产品能算出 25% 和 45% 两个'都对'的数。"

### 新手最容易踩的错误统计方式

1. **分母错用"当天活跃的新用户"**：注册了但当天没打开的人被踢出分母，留存率能算出 100%。
2. **时间窗口没关**：统计"次日回访"时没有限定次日当天，之后几天的回访也混进来。
3. **只看登录埋点**：免登录浏览（内容社区的常态）不算活跃，把"回来了但没登录"的用户判成流失。

## 四、【探案任务】

> ⏱️ **限时挑战**：第 2 步建议计时 **5 分钟**完成"限时解码"。

### 第 1 步 · 口径对齐

阿花要回答老板"改版是不是吓跑了新用户"，应该用哪个口径？

- A. 全量用户次日留存（和隔壁报表组对齐）
- B. 新增用户次日留存，分母 = 9-20 全部新增 20 人，活跃 = 登录 ∪ 浏览
- C. 新增用户次日留存，分母 = 9-20 当天活跃过的新用户

<details>
<summary>点击核对答案</summary>

**选 B**。老板问的是"新用户留不留得住"（新增口径）；分母必须是**全部新增**（注册了但当天没打开的人也在衡量范围内，他们恰恰是新手引导的失败样本）；分子的"活跃"要含免登录浏览——阿花那个"半夜刷两小时菜谱"的用户，就是被登录口径弄丢的。A 和历史 45% 不可比（口径不同），C 的分母偷换会让留存虚高甚至超 100%。

</details>

### 第 2 步 · 基础核算（限时 5 分钟）

按口径 B 写出 SQL：9-20 批次的真实次日留存率。注意"次日"窗口必须严格限定在 9-21 当天。

<details>
<summary>卡住了？点击看提示</summary>

两个 CTE：`new_users` 取 9-20 注册的人；`next_day_active` 用 `UNION` 合并 9-21 的登录与浏览（`UNION` 自带去重）。`LEFT JOIN` 后 `COUNT(DISTINCT a.user_id) / COUNT(*)`。

</details>

### 第 3 步 · 真相追踪

真实留存是 45%，报表只有 25%——20 个百分点去哪了？写 SQL 回答三个问题：① 哪些用户"次日无登录却有浏览"（缺失数据）？② 9-21 各回访用户的登录时刻（时间窗口）？③ 把分母错成"当天活跃的新用户"会算出什么（口径验证）？

<details>
<summary>点击看提示</summary>

① `LEFT JOIN` 登录表和浏览表，`HAVING` 筛"无登录且有浏览"；② 直接 `SELECT` 9-21 的登录记录看时间；③ 分母换成当天活跃的 8 人再算一遍，看看能荒谬到什么程度。

</details>

## 五、【真相大白】

### 5.1 异常根因拆解

真实留存 **45.0%**（9/20），与历史基线完全一致——**改版是清白的，回滚可以叫停**。那 20 个百分点是三件事叠加：

1. **时间窗口（-20pp 的主因）**：阿花的报表是 9-21 **18:00** 拉的，但窗口数据"到当刻为止"。当晚 20:30 才登录的 n6、20:05 和 21:40 才浏览的 n8、n9 都还没进来——报表时点只能算出 5/20 = 25%。**次日还没过完就看次日留存，天生偏低。**
2. **缺失数据（被登录口径吞掉的 3 人）**：n7、n8、n9 次日都回来了，但登录埋点丢失（免登录浏览正常上报）。只数登录埋点，这 3 人被误判流失。用 `page_view_log` 交叉验证，人全部找回。
3. **口径暗礁（差点背锅的全量报表）**：隔壁报表组的 62.5% 是**全量用户次日留存**（9-20 活跃 16 人、次日回访 10 人）。它天然比新增留存高——两个口径没有谁错，但绝不能互相对比，更不能各自和历史基线混着比。

### 5.2 参考答案 SQL（逐行注释）

```sql
USE case03_retention;

-- 【第2步 · 正确答案：9-20 批次真实次日留存】
WITH new_users AS (
  SELECT user_id
  FROM user_register
  WHERE DATE(register_time) = '2026-09-20'          -- 分母：9-20 全部新增 20 人
),
next_day_active AS (
  SELECT user_id FROM user_login
  WHERE DATE(login_time) = '2026-09-21'             -- 次日登录（窗口严格关在 9-21 当天）
  UNION                                             -- UNION 自带去重：又登又浏览只算一次
  SELECT user_id FROM page_view_log
  WHERE DATE(view_time) = '2026-09-21'              -- 次日免登录浏览也算"回来了"
)
SELECT
  COUNT(*)                                    AS new_users,      -- 20
  COUNT(DISTINCT a.user_id)                   AS returned,       -- 9
  ROUND(COUNT(DISTINCT a.user_id) / COUNT(*) * 100, 1) AS retention_pct  -- 45.0
FROM new_users n
LEFT JOIN next_day_active a ON a.user_id = n.user_id;

-- 【第3步-① · 找回"回来了但没登录"的用户】
WITH new_users AS (
  SELECT user_id FROM user_register WHERE DATE(register_time) = '2026-09-20'
)
SELECT
  n.user_id,
  MAX(CASE WHEN l.user_id IS NOT NULL THEN 1 ELSE 0 END) AS has_next_login, -- 次日是否登录
  MAX(CASE WHEN p.user_id IS NOT NULL THEN 1 ELSE 0 END) AS has_next_view   -- 次日是否浏览
FROM new_users n
LEFT JOIN user_login l
       ON l.user_id = n.user_id AND DATE(l.login_time) = '2026-09-21'
LEFT JOIN page_view_log p
       ON p.user_id = n.user_id AND DATE(p.view_time) = '2026-09-21'
GROUP BY n.user_id
HAVING has_next_login = 0 AND has_next_view = 1       -- 无登录却有浏览 = 登录埋点缺失
ORDER BY n.user_id;
-- 结果：n7、n8、n9 三人——登录埋点缺失，但人在社区里

-- 【第3步-② · 时间窗口：报表时点 vs 全天】
SELECT user_id, login_time
FROM user_login
WHERE user_id IN ('n1','n2','n3','n4','n5','n6')
  AND DATE(login_time) = '2026-09-21'
ORDER BY login_time;
-- 结果：n1~n5 在 18:00 前登录；n6 在 20:30——阿花拉报表时他还没回来

-- 【第3步-③ · 口径验证：分母错用"当天活跃的新用户"】
WITH new_users AS (
  SELECT user_id FROM user_register WHERE DATE(register_time) = '2026-09-20'
),
active_20 AS (
  SELECT user_id FROM user_login WHERE DATE(login_time) = '2026-09-20'
),
next_day_active AS (
  SELECT user_id FROM user_login  WHERE DATE(login_time) = '2026-09-21'
  UNION
  SELECT user_id FROM page_view_log WHERE DATE(view_time) = '2026-09-21'
)
SELECT
  COUNT(*)                                        AS denominator_wrong, -- 8（分母被偷换）
  COUNT(DISTINCT a.user_id)                       AS returned,          -- 8
  ROUND(COUNT(DISTINCT a.user_id) / COUNT(*) * 100, 1) AS retention_pct_wrong  -- 100.0
FROM (SELECT n.user_id FROM new_users n
      JOIN active_20 a20 ON a20.user_id = n.user_id) t
LEFT JOIN next_day_active a ON a.user_id = t.user_id;
-- 结果：100.0%！当天活跃的 8 人次日全回来了——留存率超过常识（>90%）时，
-- 第一反应是分母被偷换了：注册但当天没打开的用户才是新手引导的失败样本

-- 【口径对照 · 全量用户次日留存（隔壁报表组的 62.5%）】
WITH active_20 AS (
  SELECT user_id FROM user_login WHERE DATE(login_time) = '2026-09-20'
),
active_21 AS (
  SELECT user_id FROM user_login WHERE DATE(login_time) = '2026-09-21'
)
SELECT
  COUNT(*)                                         AS active_users_20,   -- 16
  COUNT(DISTINCT a.user_id)                        AS returned_21,       -- 10
  ROUND(COUNT(DISTINCT a.user_id) / COUNT(*) * 100, 1) AS full_retention_pct  -- 62.5
FROM active_20 o LEFT JOIN active_21 a ON a.user_id = o.user_id;
```

### 5.3 错误写法对比

**错误写法一：分母错用"当天活跃的新用户"**

```sql

  SELECT user_id FROM user_register WHERE DATE(register_time) = '2026-09-20'
),

  SELECT user_id FROM user_login WHERE DATE(login_time) = '2026-09-20'
),
next_day_active AS (
  SELECT user_id FROM user_login  WHERE DATE(login_time) = '2026-09-21'
  UNION
  SELECT user_id FROM page_view_log WHERE DATE(view_time) = '2026-09-21'

SELECT COUNT(*) AS denominator_wrong,                                -- 8（分母被偷换）
       COUNT(DISTINCT a.user_id) AS returned,                        -- 8
       ROUND(COUNT(DISTINCT a.user_id) / COUNT(*) * 100, 1) AS retention_pct_wrong  -- 100.0
FROM (SELECT n.user_id FROM new_users n
      JOIN active_20 a20 ON a20.user_id = n.user_id) t
LEFT JOIN next_day_active a ON a.user_id = t.user_id;
```

错在哪：分母 8 人、分子也是 8 人，能算出 **100.0%** 的"完美留存"。**留存率高到违背常识时，先查分母**——注册了却没打开的用户是新手引导的失败样本，恰恰是留存指标最该盯的人群。

**错误写法二：时间窗口没关**

```sql
-- 错：把 9-21 之后"任何一天"的回访都算成次日留存
WITH new_users AS (
  SELECT user_id FROM user_register WHERE DATE(register_time) = '2026-09-20'
),
any_active AS (
  SELECT user_id FROM user_login  WHERE login_time >= '2026-09-21'
  UNION
  SELECT user_id FROM page_view_log WHERE view_time >= '2026-09-21'
)
SELECT COUNT(*) AS new_users,                                        -- 20
       COUNT(DISTINCT a.user_id) AS returned_any,                    -- 11
       ROUND(COUNT(DISTINCT a.user_id) / COUNT(*) * 100, 1) AS retention_pct_wrong  -- 55.0
FROM new_users n
LEFT JOIN any_active a ON a.user_id = n.user_id;
```

错在哪：9-22 才首次回访的 n10、n11（仅浏览）也被算进来，11/20 = **55.0%**，虚高 **10 个百分点**。`WHERE login_time >= '2026-09-21'` 和 `WHERE DATE(login_time) = '2026-09-21'` 差的不是一个写法，是口径的命门。

## 六、【侦探办案笔记】

### 本关指标口径总结

- 次日留存四要素：**分母人群、活跃定义、时间窗口、数据完备性**——差一件，数字差一倍。
- 新增留存看拉新质量，全量留存看产品粘性；两者永不相比，各自有各自的历史基线。
- 留存率超过常识上限（>90%）或跌破历史下限，先怀疑分母和数据完整性，再怀疑业务。
- 内容社区类产品，"活跃"必须定义是否含免登录浏览，并用浏览日志交叉验证登录埋点。

### 业务方对齐口径的标准提问话术

1. "这个留存是**新增口径还是全量口径**？历史基线是哪一个的？"
2. "分子里的'活跃'**含不含免登录浏览**？分母是**全部新增还是当天活跃的新增**？"
3. "报表是**几点拉的**？次日还没结束的时候，这个数字只能当参考。"

### 同类异常排查的通用方法论

"留存缩水"类案件四步走：

1. **复现两个数字**：确认两份报表各自的分子分母 SQL；
2. **查窗口**：报表生成时点是否早于窗口结束？统计窗口是否没关严？
3. **找缺失**：用另一个行为源（浏览/曝光/服务端日志）交叉验证"疑似流失"用户；
4. **再谈业务**：以上全排除，才轮到改版、渠道质量这些业务假设。
