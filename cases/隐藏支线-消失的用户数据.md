## 一、【案情通报】

咕噜严选的 9 月经营数据要走年度审计，三笔账卡住了：

1. **注册对不上**：`user_register` 表 9 月有 **12 条注册记录**，但风控的设备指纹分析说真人只有 **10 个**——有人换了渠道重复注册？
2. **首购查无此人**：首购付费用户 12 人，其中 **u11、u12 两个人在注册表里不存在**。他们从哪来的？钱是真的吗？
3. **GMV 对不齐**：数仓汇总表 `dwd_gmv_daily` 合计 **5440 元**，订单明细表实付合计只有 **5000 元**，差 **8.8%**。数仓组说明细漏数了，业务组说汇总多数了。

**任务目标**：用多表联查与窗口函数逐笔结案：注册去重、孤儿订单溯源、GMV 逐日对账，给出每一分差异的去向，让三方都能签字。

## 二、【指标卷宗】数据对账：让三张表互相作证

对账类案件的通用思想：**同一事实必须有多个数据源，源与源对不上，差异本身就是线索**。

### 口径 A：真实注册口径（去重后）

- **计算逻辑**：`ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY register_time)` 取每用户最早一条为"真实注册"，其余标记为重复。
- **适用场景**：换设备/换渠道重复注册的清洗，新增用户数的标准算法。
- **歧义坑点**：`COUNT(*)` 数的是记录数不是人数；"最早一条"还是"最新一条"作为真实注册，会影响注册渠道归因——要与业务约定。

### 口径 B：孤儿订单口径（有下游、无上游）

- **计算逻辑**：订单表 `LEFT JOIN` 去重后的注册表，`WHERE r.user_id IS NULL` 找出"花钱了但查无注册"的用户。
- **适用场景**：埋点/同步链路断裂检测，资金安全审计。
- **歧义坑点**：孤儿用户不一定是假数据——一键登录、老系统迁移、注册事件丢失都会产生；**先核资金流水，再定性**。

### 口径 C：GMV 逐日对账口径

- **计算逻辑**：明细表按天 `SUM(pay_amount)`（`paid` 口径），与数仓汇总表按天 `JOIN` 比对，差异行即事故现场。
- **适用场景**：数仓任务巡检、财报对账。
- **歧义坑点**：退款单误计入、任务双跑（同一天数据叠加）、分区重叠——三种病在总量上合成一个 8.8%，**只有逐日对账才能拆开**。

### 行业差异速记

| 行业 | 对账重点 | 特殊之处 |
|---|---|---|
| 电商 | GMV 明细 vs 汇总、订单 vs 注册 | 退款回冲与拆单合并都要在对账口径里写明 |
| 在线教育 | 学费实收 vs 财务账、到课 vs 报名 | 递延收入（课程未上完）使对账周期更长 |
| 内容平台 | 收入流水 vs 渠道对账单 | 打赏分成、广告填充的多方结算对账更复杂 |

### 面试标准回答话术

> "数据对账我会做三层：**行数对账**（记录数 vs 去重人数，抓重复注册）、**链路对账**（下游 LEFT JOIN 上游找孤儿，抓链路断裂）、**金额逐期对账**（按天/按分区 JOIN 比差异，抓双跑与口径误计）。总量差异是症状，逐期差异才是病历。"

### 新手最容易踩的错误统计方式

1. **只对总量不对明细**：8.8% 的差异对不出原因，就无法修复——必须下钻到差异日期。
2. **注册数直接 `COUNT(*)`**：重复注册让"新增用户数"虚增，月度环比失真。
3. **对账口径不对称**：明细剔了退款、汇总没剔（或反之），对账永远差一个固定值。

## 四、【探案任务】

> ⏱️ **限时挑战**：本关不设单点计时，建议整案控制在 **90 分钟**内；第 4 步的对账 SQL 是全案决胜点，可给自己 10 分钟。

### 第 1 步 · 口径对齐

三笔账需要三个口径。请先口头回答：**"9 月新增用户数"应该用记录数还是去重人数？"GMV"应该用哪个口径对账？**

<details>
<summary>点击核对答案</summary>

新增用户数 = 去重后的真实注册人数（每用户取最早一条注册记录）；GMV 对账必须**两侧同口径**（明细 paid 实付 vs 汇总 paid 实付），且**逐日比对**而非只比总量——总量差异是症状，逐日差异才是病历。

</details>

### 第 2 步 · 基础核算

用 `ROW_NUMBER()` 窗口函数完成注册去重：输出"表内记录数 vs 真实人数"，并列出重复注册的用户清单。

<details>
<summary>点击看提示</summary>

`ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY register_time)` 给同一用户的多次注册编号，`rn = 1` 为真实注册。重复用户清单用 `GROUP BY user_id HAVING COUNT(*) > 1`。

</details>

### 第 3 步 · 真相追踪（上）：孤儿订单

找出"有订单、查无注册"的用户及其付费金额。**注意**：JOIN 的注册表必须先去重，否则重复注册会让孤儿判断失真。

<details>
<summary>点击看提示</summary>

CTE `reg_ranked` 取 `rn = 1` 的注册名单，订单表 `LEFT JOIN` 它，`WHERE r.user_id IS NULL`。孤儿用户的累计付费可用 `SUM(...) OVER (PARTITION BY user_id)` 窗口聚合。

</details>

### 第 4 步 · 真相追踪（下）：GMV 逐日对账

明细按天聚合后与数仓汇总表逐日 `JOIN`，输出差异日期与差异金额；再用 `LAG()` 观察双跑日的曲线形态。

<details>
<summary>点击看提示</summary>

明细侧 `WHERE order_status = 'paid'`（与汇总同口径）；差异行 `WHERE m.gmv <> COALESCE(a.gmv, 0)`。`LAG(gmv) OVER (ORDER BY stat_date)` 看 9-21 前后：0 → 360 → 0 的孤立尖峰是任务双跑的经典形态。

</details>

## 五、【真相大白】

### 5.1 异常根因拆解

三笔账、三个根因，全部落定：

1. **注册表 12 条记录 = 10 个真人**：u05（9-03 与 9-15）和 u09（9-14 与 9-22）各重复注册一次——换渠道重进、注册接口未幂等。**9 月新增用户数应为 10 人**，不是 12 人；重复注册还会污染渠道归因（一个人被记成两个渠道的新客）。
2. **u11、u12 = 孤儿付费用户**：两人合计付费 410 元（180 + 230），订单、金额、时间全部正常，唯独注册事件在链路中丢失（一键登录通道的注册埋点断报）。**钱是真的，人是真的，丢的是注册记录**——处理方式是补录注册事件 + 修复一键登录埋点，而不是把他们当假数据清除。
3. **GMV 差 8.8% = 两笔独立事故的叠加**：逐日对账定位到 9-18（数仓 260 vs 明细 0，+260 元，**退款单被误计入 GMV**）与 9-21（数仓 360 vs 明细 180，+180 元，**汇总任务双跑**）。5440 - 5000 = 440 元，一分不差。
4. **首购队列核验**：12 个付费用户全部在 9 月完成首购，首购订单 GMV 合计 3838 元——复购订单（u01、u02 的第二单）贡献剩余 1162 元。队列本身无异常。

### 5.2 参考答案 SQL（逐行注释）

```sql
USE case_hidden_audit;

-- 【第2步 · 注册对账：12 条记录 vs 10 个真人】
WITH reg_ranked AS (
  SELECT
    user_id,
    register_time,
    channel,
    ROW_NUMBER() OVER (PARTITION BY user_id       -- 同一用户的多条注册
                       ORDER BY register_time) AS rn  -- 按时间排名：1 = 真实注册
  FROM user_register
)
SELECT
  (SELECT COUNT(*) FROM user_register)               AS raw_rows,   -- 12 条记录
  (SELECT COUNT(*) FROM reg_ranked WHERE rn = 1)     AS real_users  -- 10 个真人
FROM DUAL;

-- 【第2步补充 · 重复注册用户清单】
SELECT user_id, COUNT(*) AS reg_cnt,
       MIN(register_time) AS first_reg,   -- 真实注册时间（去重保留这条）
       MAX(register_time) AS last_reg     -- 重复注册时间
FROM user_register
GROUP BY user_id
HAVING COUNT(*) > 1;
-- 结果：u05（9-03 / 9-15）、u09（9-14 / 9-22）

-- 【第3步 · 孤儿付费用户：有订单、查无注册】
WITH reg_ranked AS (
  SELECT user_id,
         ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY register_time) AS rn
  FROM user_register
),
real_users AS (
  SELECT user_id FROM reg_ranked WHERE rn = 1   -- 先去重，再 JOIN
)
SELECT DISTINCT
  o.user_id,
  SUM(o.pay_amount) OVER (PARTITION BY o.user_id) AS total_paid,  -- 窗口聚合：该用户累计付费
  MIN(o.order_time) OVER (PARTITION BY o.user_id) AS first_order_time
FROM order_info o
LEFT JOIN real_users r ON r.user_id = o.user_id
WHERE r.user_id IS NULL;                               -- 注册表查无此人
-- 结果：u11 付费 180、u12 付费 230——链路丢的是注册事件，不是钱

-- 【真相3 · 首购队列核验】
WITH orders_ranked AS (
  SELECT user_id, order_id, order_time, pay_amount,
         ROW_NUMBER() OVER (PARTITION BY user_id
                            ORDER BY order_time) AS rn   -- 每用户按下单时间排名：1 = 首购
  FROM order_info
  WHERE order_status = 'paid'
)
SELECT COUNT(*) AS first_purchase_users,               -- 12 人
       ROUND(SUM(pay_amount), 2) AS first_order_gmv    -- 首购 GMV 合计 3838 元
FROM orders_ranked
WHERE rn = 1;

-- 【第4步 · GMV 逐日对账：差异行即事故现场】
WITH actual AS (
  SELECT DATE(order_time) AS d,
         SUM(pay_amount) AS gmv          -- 明细侧：paid 实付口径，与汇总对齐
  FROM order_info
  WHERE order_status = 'paid'
  GROUP BY DATE(order_time)
)
SELECT
  m.stat_date,
  m.gmv                             AS dwd_gmv,
  COALESCE(a.gmv, 0)                AS actual_gmv,
  ROUND(m.gmv - COALESCE(a.gmv, 0), 2) AS diff   -- 正数 = 数仓多记
FROM dwd_gmv_daily m
LEFT JOIN actual a ON a.d = m.stat_date
WHERE m.gmv <> COALESCE(a.gmv, 0)                     -- 只看差异行
ORDER BY m.stat_date;
-- 结果：9-18 数仓 260 / 明细 0（退款误计 +260）；9-21 数仓 360 / 明细 180（双跑 +180）

-- 【第4步补充 · 总账核验：440 元一分不差】
SELECT
  (SELECT SUM(gmv) FROM dwd_gmv_daily)  AS dwd_total,     -- 5440.00
  (SELECT SUM(pay_amount) FROM order_info
    WHERE order_status = 'paid')          AS actual_total, -- 5000.00
  ROUND(((SELECT SUM(gmv) FROM dwd_gmv_daily) -
         (SELECT SUM(pay_amount) FROM order_info WHERE order_status='paid')) /
        (SELECT SUM(pay_amount) FROM order_info WHERE order_status='paid') * 100, 1)
    AS gap_pct                                            -- 8.8%
FROM DUAL;

-- 【第4步扩展 · LAG 环比：双跑日的孤立尖峰形态】
SELECT stat_date, gmv,
       LAG(gmv) OVER (ORDER BY stat_date) AS prev_day_gmv  -- 前一日 GMV
FROM dwd_gmv_daily
WHERE stat_date BETWEEN '2026-09-17' AND '2026-09-24'
ORDER BY stat_date;
-- 结果：9-20 为 0 → 9-21 突现 360 → 9-22 归 0，"孤立尖峰"是任务双跑的经典曲线形态
```

### 5.3 错误写法对比

**错误写法一：注册数直接 `COUNT(*)`（重复注册计入新增）**

```sql
SELECT COUNT(*) AS new_users FROM user_register;   -- 错：12 条 ≠ 12 人
```

错在哪：得出 **12 人**，真实只有 **10 人，虚增 2 人（+20%）**。重复注册让月度新增虚高、渠道归因错乱（u05 会被同时记成 search 和 feed_ads 的新客）。凡"人数"必去重，凡去重必定"保留哪条"的规则（本案：最早一条）。

**错误写法二：只对总量不对明细（对账对了个寂寞）**

```sql
SELECT (SELECT SUM(gmv) FROM dwd_gmv_daily) -
       (SELECT SUM(pay_amount) FROM order_info WHERE order_status='paid') AS gap;  -- 440
```

错在哪：440 元的差异**算得出来、解释不了**——数仓组坚称"明细漏了 440"，业务组坚称"汇总多了 440"，三方继续僵持。加上 `GROUP BY DATE(order_time)` 逐日比对，差异立刻定位到 9-18（+260，退款误计）与 9-21（+180，双跑），**两个修复动作当天就能下发**。对账的价值不在"差多少"，在"差在哪"。

## 六、【侦探办案笔记】

### 本关指标口径总结

- 对账三层法：**行数对账**（记录数 vs 去重人数）、**链路对账**（下游 LEFT JOIN 上游找孤儿）、**金额逐期对账**（按天 JOIN 比差异）。
- 窗口函数三板斧：`ROW_NUMBER()` 去重取"最早一条"、`SUM() OVER (PARTITION BY)` 窗口聚合、`LAG()` 看时序形态（孤立尖峰 = 双跑指纹）。
- 孤儿数据先核资金再定性：**链路丢记录 ≠ 用户造假**，补录比清除更专业。
- 总量差异是症状，逐期差异是病历——修复动作必须落到具体日期和具体任务。

### 业务方对齐口径的标准提问话术

1. "对账的**两侧口径**一致吗？明细剔退款了吗？汇总表用的哪个版本的任务产出？"
2. "重复注册**保留哪条**？最早还是最新？渠道归因跟着哪条走？"
3. "孤儿用户**有没有资金流水可核**？核过了再决定补录还是清除。"

### 同类异常排查的通用方法论

"三笔账对不上"类案件（审计级）四步走：

1. **先各自验真**：每张表单独做完整性体检（重复、空值、字段一致性）；
2. **再互相作证**：注册 ↔ 订单（链路对账）、明细 ↔ 汇总（金额对账），差异落日期；
3. **差异定性**：每笔差异归入"重复 / 丢失 / 误计 / 双跑"四类，各配修复动作；
4. **出具对账报告**：总量差异 → 差异明细 → 修复清单 → 防复发机制（任务幂等、注册接口去重、退款对账告警）。
