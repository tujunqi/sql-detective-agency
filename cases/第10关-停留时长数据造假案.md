## 一、【案情通报】

深夜食记是美食内容社区，用户看菜谱、刷教程。9 月的内容周报显示：**人均会话停留时长 23.0 分钟**，历史基线一直在 8 分钟上下。内容组兴高采烈，庆功宴都订了。

老吴的三个疑点：

1. **体感对不上**：他自己重度使用半小时，内容质量没有跳变式提升；
2. **配侧行为没跟涨**：点赞、收藏、关注率纹丝不动——时长翻倍但互动没变，违背常识；
3. **用户反馈里有人吐槽**："昨晚看菜谱睡着了，早上醒来发现 App 还开着，结果我的'使用时长'吓死人。"

**任务目标**：还原 9 月真实的人均停留时长，判定 23 分钟里有多少是"真实内容消费"、多少是"统计事故"，并给出经得起庆功宴检验的口径。

## 二、【指标卷宗】人均停留时长：均值的三重绑架

**人均停留时长** = 统计周期内有效停留时间合计 ÷ 会话数（或用户数）。均值类指标对异常值毫无抵抗力。

### 口径 A：会话均长（截断版，行业标准）

- **计算逻辑**：单会话时长按 `leave_time - enter_time` 计算，但**先做两道处理**——剔除跨天挂起会话（离开日期 ≠ 进入日期），单会话截断上限（常见 30 分钟）；再求均值。
- **适用场景**：内容平台的时长健康度，行业通用的稳健口径。
- **歧义坑点**：不截断、不剔挂起，均值直接被极值绑架——23 分钟就是这么来的。

### 口径 B：人均时长（按用户）

- **计算逻辑**：有效时长合计 ÷ 去重活跃用户数。
- **适用场景**：和 DAU 搭配看"用户粘性总账"。
- **歧义坑点**：重度用户一天 10 个会话，会把人均拖高；要配"活跃天数"一起解读。

### 口径 C：中位数（稳健统计）

- **计算逻辑**：会话时长的中位数，不受极值影响。
- **适用场景**：与均值并列汇报——**均值与中位数差距越大，说明分布越偏、极值越重**，本身就是数据质量的报警器。
- **歧义坑点**：中位数偏低是常态（多数会话短），不能单独拿中位数说"时长很差"，要均值中位数一起看。

### 行业差异速记

| 行业 | 时长口径习惯 | 特殊之处 |
|---|---|---|
| 内容平台 | 会话均长 + 人均时长双口径 | 必须处理后台挂起：切后台、忘关页、推送拉起 |
| 在线教育 | 有效学习时长（心跳上报） | 挂机听课要靠心跳剔除，视频暂停也计入的口径有争议 |
| 工具 App | 通常不看时长，看频次与留存 | 强行报时长容易被"忘关页"绑架 |

### 面试标准回答话术

> "停留时长我会先钉统计逻辑：**会话怎么切**（30 分钟无行为切一段）、**挂起怎么剔**（跨天或超上限截断）、**均值还是中位数**（两者并列，差距大说明极值重）。上报前我会做一次字段一致性校验——`stay_seconds` 和时间戳差值对不上的，上游统计逻辑本身就有病。"

### 新手最容易踩的错误统计方式

1. **直接 `AVG(stay_seconds)`**：对极值零防御，一条挂起 3.5 小时的会话能拉飞 40 条正常记录的均值。
2. **不做字段一致性校验**：上游算好的 `stay_seconds` 直接信，时间戳对不上都不知道。
3. **只看均值不看中位数**：分布严重右偏时，均值讲的是"极值的故事"，中位数讲的才是"多数人的故事"。

## 四、【探案任务】

> ⏱️ **限时挑战**：第 2 步建议计时 **5 分钟**完成"限时解码"。

### 第 1 步 · 口径对齐

给庆功宴（或者取消庆功宴）用的时长口径，应该怎么定？

- A. 直接 `AVG(stay_seconds)`（报表现状，23.0 分钟）
- B. 剔除跨天会话后求均值
- C. 剔除跨天会话 + 单会话截断 30 分钟后求均值，并列中位数

<details>
<summary>点击核对答案</summary>

**选 C**。A 对极值零防御；B 只剔了 2 条跨天的，同天超长挂起（s0038 挂了 2.7 小时、只看了 5 页）还在，深度会话也没截断——"多数人的真实体验"仍被少数会话绑架。C 的截断让"单会话贡献"封顶，中位数并列兜底。**注意**：深度会话（s0035/s0036，页数 40+）是真消费，截断不是删除——它们对均值的贡献被限制在 30 分钟内，而不是被清零。

</details>

### 第 2 步 · 基础核算（限时 5 分钟）

按口径 C 写出修正后的人均会话时长（分钟，保留 1 位小数）。

<details>
<summary>卡住了？点击看提示</summary>

`WHERE DATE(leave_time) = DATE(enter_time)` 剔跨天；`AVG(LEAST(stay_seconds, 1800))` 截断 30 分钟；除以 60 转分钟。三个动作一条 SQL 完成。

</details>

### 第 3 步 · 真相追踪

23 分钟的水分构成：① 找出全部跨天挂起会话（`leave` 的自然日 ≠ `enter` 的自然日）；② 列出 TOP5 超长会话，看"时长 vs 页数"的比值——挂起会话挂 2~3.5 小时却只看几页；③ 做一次字段一致性校验：`stay_seconds` 是否都等于 `TIMESTAMPDIFF(SECOND, enter_time, leave_time)`？

<details>
<summary>点击看提示</summary>

③ 一条 `SELECT COUNT(*) ... WHERE stay_seconds <> TIMESTAMPDIFF(SECOND, enter_time, leave_time)`——计数为 0 说明上游字段可信；不为 0，说明统计逻辑本身有 bug，比挂起更严重。

</details>

## 五、【真相大白】

### 5.1 异常根因拆解

**修正后的人均会话时长 = 8.9 分钟**，回到历史水位——内容质量没有跳变，庆功宴取消。23.0 分钟的水分构成：

1. **后台挂起（主犯，贡献最大）**：3 条挂起会话——s0037 从 23:10 挂到次日 02:40（**3.5 小时**，只看 8 页）、s0039 同样跨天挂 2.4 小时、s0038 同天挂 2.7 小时只看 5 页。**"时长 2~3 小时、页数个位数"的比值是挂起的铁证**——用户切了后台或睡前忘关页，`leave_time` 停在几十小时后。其中 2 条跨天会话还污染了 9-21、9-29 的"当日数据"。
2. **极值未截断（从犯）**：2 条真实深度会话（s0035/s0036，40+ 页、70~80 分钟）是真消费，但均值对它们毫无防御；截断到 30 分钟后，它们仍然贡献了合理的时长份额，只是不再绑架均值。
3. **统计逻辑（方法论缺陷）**：报表直接 `AVG(stay_seconds)`，既不剔挂起也不截断，也不做字段一致性校验。字段校验结果为 0 异常——`stay_seconds` 本身可信，**问题出在"拿来就用"的统计姿势**。

### 5.2 参考答案 SQL（逐行注释）

```sql
USE case10_duration;

-- 【报表现状 · 原始均值（被绑架的 23 分钟）】
SELECT
  COUNT(*)                          AS sessions,          -- 40 条
  ROUND(AVG(stay_seconds), 0)       AS avg_seconds_raw,   -- 1382 秒
  ROUND(AVG(stay_seconds) / 60, 1)  AS avg_minutes_raw    -- 23.0 分钟
FROM user_stay_log;

-- 【第3步-① · 跨天挂起会话：离开日期 ≠ 进入日期】
SELECT session_id, user_id, enter_time, leave_time, stay_seconds
FROM user_stay_log
WHERE DATE(leave_time) <> DATE(enter_time);
-- 结果：s0037（23:10 → 次日 02:40，挂 3.5 小时）、s0039（23:50 → 次日 02:13，挂 2.4 小时）

-- 【第2步 · 正确答案：剔跨天 + 截断 30 分钟后的会话均长】
SELECT
  COUNT(*)                                        AS valid_sessions,     -- 38 条
  ROUND(AVG(LEAST(stay_seconds, 1800)), 0)        AS avg_seconds_fixed,  -- 534 秒
  ROUND(AVG(LEAST(stay_seconds, 1800)) / 60, 1)   AS avg_minutes_fixed   -- 8.9 分钟
FROM user_stay_log
WHERE DATE(leave_time) = DATE(enter_time);          -- 剔除跨天挂起

-- 【口径 C · 中位数并列：多数会话的真实水位】
WITH ordered AS (
  SELECT stay_seconds,
         ROW_NUMBER() OVER (ORDER BY stay_seconds) AS rn,   -- 时长排序编号
         COUNT(*) OVER ()                          AS cnt   -- 总会话数（窗口计数）
  FROM user_stay_log
  WHERE DATE(leave_time) = DATE(enter_time)
)
SELECT ROUND(AVG(stay_seconds), 0) AS median_seconds      -- 中位数 = 420 秒 = 7.0 分钟
FROM ordered
WHERE rn IN (FLOOR((cnt + 1) / 2), CEILING((cnt + 1) / 2));
-- 偶数个样本取中间两位的平均；均值 8.9 分钟 vs 中位数 7.0 分钟，分布右偏但已可用

-- 【第3步-② · TOP5 超长会话：时长与页数的比值定罪】
SELECT session_id, user_id, enter_time, leave_time, stay_seconds,
       ROUND(stay_seconds / 3600, 1) AS stay_hours,        -- 折算小时，刺眼
       page_count,
       ROUND(stay_seconds / page_count, 0) AS sec_per_page -- 每页停留秒数：挂起会话高得离谱
FROM user_stay_log
ORDER BY stay_seconds DESC
LIMIT 5;
-- 结果：TOP3 时长 2.4~3.5 小时、页数 5~8（每页上千秒）；深度会话 TOP2 页数 40+（每页约百秒）

-- 【第3步-③ · 字段一致性校验：上游可信吗】
SELECT COUNT(*) AS mismatch_cnt    -- 0：stay_seconds 与时间戳差值全部一致
FROM user_stay_log
WHERE stay_seconds <> TIMESTAMPDIFF(SECOND, enter_time, leave_time);

-- 【错误写法对照 · 只剔跨天、不截断】
SELECT COUNT(*)                              AS valid_sessions,   -- 38
       ROUND(AVG(stay_seconds) / 60, 1)      AS avg_minutes_half  -- 14.9 分钟
FROM user_stay_log
WHERE DATE(leave_time) = DATE(enter_time);
```

### 5.3 错误写法对比

**错误写法一：直接 AVG（报表现状）**

```sql
SELECT ROUND(AVG(stay_seconds) / 60, 1) AS avg_minutes FROM user_stay_log;  -- 错
```

错在哪：算出 **23.0 分钟**，比修正值 8.9 **虚高 14.1 分钟（+158%）**。3 条挂起会话贡献了 31000 秒（占全表 56% 的"时长"），却几乎没有真实消费（页数 5~8）。庆功宴请的是这三条会话，不是用户。

**错误写法二：只剔跨天、不截断**

```sql
SELECT ROUND(AVG(stay_seconds) / 60, 1) AS avg_minutes
FROM user_stay_log
WHERE DATE(leave_time) = DATE(enter_time);   -- 错：洗了一半
```

错在哪：算出 **14.9 分钟**，仍比修正值虚高 6.0 分钟（+67%）。同天超长挂起（s0038 挂 2.7 小时看 5 页）和未截断的深度会话继续绑架均值。**剔除跨天是"把明显坏的扔掉"，截断是"把好的也限制火力"——两道工序缺一不可。**

## 六、【侦探办案笔记】

### 本关指标口径总结

- 均值类指标的三道防线：**剔挂起（跨天识别）、截断上限（30 分钟惯用）、中位数并列**。
- "时长 × 页数"的比值是挂起照妖镜：真消费每页百秒级，挂起每页千秒级。
- 深度会话是真实资产：截断不是删除，是限制它们对均值的绑架力。
- 上游字段先校验再使用：`stay_seconds` 与 `TIMESTAMPDIFF` 对不上的表，整张表都不能直接信。

### 业务方对齐口径的标准提问话术

1. "这个时长的**统计口径**：会话怎么切？截断上限是多少？挂起剔不剔？"
2. "报的是**会话均长还是人均时长**？两个数差距大吗？"
3. "**均值和中位数**一起看吗？差得多说明什么，团队里有共识吗？"

### 同类异常排查的通用方法论

"均值被绑架"类案件三步走：

1. **分布体检**：均值 vs 中位数、TOP10 极值清单——极值的"时长/页数"比值定性质；
2. **按物理意义过滤**：跨天、超上限、页数为 0 的会话，逐一归类（挂起/真实/脏数据）；
3. **双口径重建**：截断均值 + 中位数并列发布，庆功宴（或事故复盘）用同一套数。

### 解锁成就徽章

🏆 **「时长裁判」**——你取消了庆功宴，也保住了内容组的公信力：数据没涨，但谁也没造假，只是均值被人质化了。经验 +15%，侦探等级：**A级侦探**（第 8 枚徽章达成）。徽章档案见 [成就徽章系统](../docs/成就徽章系统.md)。
