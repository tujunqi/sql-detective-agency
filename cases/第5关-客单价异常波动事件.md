## 一、【案情通报】

咕噜严选 10 月 1 日 ~ 7 日搞了"满 199 减 30"大促。财务王姐的月度复盘卡在了一个数字上：

> "**客单价**（Average Revenue Per Order）——平均每一笔订单收多少钱。这个数关系到三件事：定价策略复盘、毛利测算、还有和去年同期对比。**报表 A 算出 73.5 元**，比活动前跌了 20%+，定价组压力大；**报表 B 算出 99.6 元**，稳中有升。两个数差了 26 块钱，总有一个是错的。"

她把两张报表的 SQL 也带来了：

- 报表 A：`SUM(非退款订单实付) / 全部订单数`
- 报表 B：`全部订单商品原价合计 / 全部订单数`

**任务目标**：算出大促周的真实客单价，判定两份报表各错在哪，并给出"客单价 + 人均实付"两个指标的正确算法（前者管订单效率，后者管用户钱包）。

## 二、【指标卷宗】客单价：分母是"单"，分子是"钱"，两头都有暗流

**客单价** = 统计周期内的支付金额 ÷ 支付订单数。公式极简，暗流三股。

### 口径 A：订单口径（标准）

- **计算逻辑**：`有效支付订单的实付金额合计 ÷ 有效支付订单数`。"有效支付" = `paid`，剔除 `refunded`（已退款）与 `cancelled`（未支付取消）。
- **适用场景**：电商运营的默认口径，反映每一笔成交的金额效率。
- **歧义坑点**：分子分母必须**同一批订单**——分子剔了退款、分母没剔（报表 A 的病），或者干脆用原价当分子（报表 B 的病），都是家常便饭。

### 口径 B：人均口径（ARPPU 视角）

- **计算逻辑**：`实付金额合计 ÷ 去重下单人数`。
- **适用场景**：衡量用户钱包份额——一个人连下三单，订单口径摊薄了金额，人均口径才看得出"这个人到底花了多少"。
- **歧义坑点**：和订单口径不是一个指标！大促"满减凑单"会同时抬高订单数和人均实付，两条曲线劈叉时要能解释。

### 口径 C：GMV 口径（商家视角）

- **计算逻辑**：`商品原价（或应付）合计 ÷ 订单数`，不扣优惠。
- **适用场景**：GMV 报表、平台补贴分析。
- **歧义坑点**：优惠越多，GMV 口径和实付口径差距越大；大促期间两者能差出 10%~20%，混用必打架。另外 GMV 口径也必须**剔除未支付订单**，否则 "cancelled" 单会稀释分母。

### 行业差异速记

| 行业 | 客单价定义 | 特殊之处 |
|---|---|---|
| 电商 | 实付口径为主，GMV 口径对账 | 满减/凑单导致拆单高发，客单价结构性下降要单独解释 |
| 在线教育 | 实付口径，按课程单 | 客单价高、频次低，一个高客单学员能拉飞均值，常配中位数 |
| 内容平台 | 电商化后同电商口径 | 打赏/会员/单点购买混杂，须先定"收入包含哪些"再谈客单 |

### 面试标准回答话术

> "客单价我会先钉三件事：**订单有效性**（剔除退款和未支付，分子分母同一批订单）、**金额口径**（用户实付还是商品原价/GMV，含不含优惠）、**拆单处理**（满减拆单会稀释客单价，通常订单口径照算，另配'人均实付'看用户钱包）。口径不同，每个数都有它的用处，但报表上必须标清楚。"

### 新手最容易踩的错误统计方式

1. **分子剔退款、分母不剔**：退款单只剩"存在感"没有"金额"，分母被虚增，客单价被砸下去。
2. **拿原价当实付**：优惠力度越大，数字越虚高，大促期间尤其严重。
3. **把未支付取消单计入分母**：用户加了购物车又取消，也算"一单"。

## 四、【探案任务】

> ⏱️ **限时挑战**：第 2 步建议计时 **5 分钟**完成"限时解码"。

### 第 1 步 · 口径对齐

给老板的"那一个数"，应该怎么算？

- A. `SUM(非退款订单实付) ÷ 全部订单数`（报表 A 的口径）
- B. `SUM(全部订单商品原价) ÷ 全部订单数`（报表 B 的口径）
- C. `SUM(paid 订单实付) ÷ paid 订单数`，另配"人均实付 = 实付合计 ÷ 去重下单人数"

<details>
<summary>点击核对答案</summary>

**选 C**。A 的分子剔了退款、分母却把退款单和未支付单都数进去（22 单），双重口径错位；B 用原价冒充实付，大促优惠把 95.1 抬成 99.6，还把未支付单算进了"客单"。C 是标准答案，同时建议老板看两个数：**客单价 95.1**（订单效率）与**人均实付 115.5**（用户钱包）。

</details>

### 第 2 步 · 基础核算（限时 5 分钟）

按口径 C 写出 SQL：有效支付订单的客单价、人均实付。

<details>
<summary>卡住了？点击看提示</summary>

客单价：`WHERE order_status='paid'` 后 `SUM(pay_amount)/COUNT(*)`；人均实付把 `COUNT(*)` 换成 `COUNT(DISTINCT user_id)`。两条 SQL 只差一个聚合函数，但含义完全不同。

</details>

### 第 3 步 · 真相追踪

三股暗流各影响多少？写 SQL：① 按 `order_status` 分组统计单数与金额（退款、取消各占多少）；② 用 `parent_order_id` 找出全部拆单组，算每组"合并后的购物意图金额"；③ 验证报表 A、B 的错法各算出多少。

<details>
<summary>点击看提示</summary>

② 自连接：`JOIN order_info child ON child.parent_order_id = parent.order_id`，主子单实付相加。③ 报表 A 的分子是 `CASE WHEN order_status <> 'refunded' THEN pay_amount ELSE 0 END`，分母 `COUNT(*)` 不加条件——跑出来对比。

</details>

## 五、【真相大白】

### 5.1 异常根因拆解

**真实客单价 95.1 元**，环比没跌——跌的是口径。两份报表各病在一处：

1. **报表 A 的 73.5：分子分母错位**。分子只算非退款单的实付（1617 元，其中未支付取消单金额本来就是 0），分母却把 22 单全数了进去——3 张退款单 + 2 张取消单贡献了 5 个"零金额分母"。**退款单被剔了钱、没剔名**，客单价被砸到 73.5，环比"暴跌"。
2. **报表 B 的 99.6：原价冒充实付**。分子用 `goods_amount`（优惠前原价合计 2191 元），大促优惠（券额合计 274 元）没扣，且未支付单照算——商家视角的"应付口径"冒充了用户视角的"实付口径"，虚高 4.5 元。
3. **拆单的暗流**：满 199 减 30 让 u01、u07、u15 三位用户各拆成主单 + 子单，3 组拆单把 17 张有效单"摊薄"出 3 个小金额子单。订单口径 95.1 依然成立，但要看用户真实花费，得看**人均实付 115.5**（= 实付合计 1617 ÷ 14 个下单用户；本例中按主子单合并的"购物意图口径"同样是 14 组、115.5 元，因为每个拆单用户只拆了一组）。

### 5.2 参考答案 SQL（逐行注释）

```sql
USE case05_aov;

-- 【第2步 · 正确客单价：有效支付订单的实付金额】
SELECT
  COUNT(*)                             AS paid_orders,  -- 17 单（paid，剔除退款与取消）
  SUM(pay_amount)                      AS paid_total,   -- 1617.00 元
  ROUND(SUM(pay_amount) / COUNT(*), 1) AS aov_correct   -- 客单价 95.1 元
FROM order_info
WHERE order_status = 'paid';                            -- 分子分母同一批订单，铁律

-- 【第2步 · 人均实付：看用户的钱包，不看单】
SELECT
  COUNT(DISTINCT user_id)                              AS paid_users,  -- 14 人
  SUM(pay_amount)                                      AS paid_total,  -- 1617.00
  ROUND(SUM(pay_amount) / COUNT(DISTINCT user_id), 1)  AS avg_per_user -- 115.5 元
FROM order_info
WHERE order_status = 'paid';

-- 【第3步-① · 状态分布：退款 3 单 234 元、取消 2 单 0 元】
SELECT
  order_status,
  COUNT(*)        AS orders,   -- 单数
  SUM(pay_amount) AS pay_sum   -- 实付合计
FROM order_info
GROUP BY order_status;
-- 结果：paid 17 单 1617；refunded 3 单 234；cancelled 2 单 0

-- 【第3步-② · 拆单组全景：主子单合并的购物意图金额】
SELECT
  parent.order_id AS main_order,
  parent.user_id,
  child.order_id  AS sub_order,
  child.pay_amount AS sub_pay,
  ROUND(parent.pay_amount + child.pay_amount, 2) AS intent_total
FROM order_info parent
JOIN order_info child ON child.parent_order_id = parent.order_id
ORDER BY parent.order_id;
-- 结果：o01+o02 = 175；o09+o10 = 143；o18+o19 = 159

-- 【拆单合并口径：14 组购物意图，115.5 元/组】
SELECT
  COUNT(DISTINCT COALESCE(parent_order_id, order_id))                      AS intent_cnt,   -- 14
  ROUND(SUM(pay_amount) / COUNT(DISTINCT COALESCE(parent_order_id, order_id)), 1) AS aov_merged -- 115.5
FROM order_info
WHERE order_status = 'paid';

-- 【错法复现 · 报表A：分子剔退款、分母照单全收】
SELECT
  COUNT(*)                                                               AS all_orders,    -- 22
  ROUND(SUM(CASE WHEN order_status <> 'refunded' THEN pay_amount ELSE 0 END)
        / COUNT(*), 1)                                                    AS aov_report_a  -- 73.5
FROM order_info;

-- 【错法复现 · 报表B：原价冒充实付 + 未支付单计入】
SELECT
  COUNT(*)                               AS all_orders,   -- 22
  ROUND(SUM(goods_amount) / COUNT(*), 1) AS aov_report_b  -- 99.6
FROM order_info;
```

### 5.3 错误写法对比

**错误写法一：报表 A（分子剔退款、分母不剔）**

```sql
SELECT ROUND(SUM(CASE WHEN order_status <> 'refunded' THEN pay_amount ELSE 0 END)
       / COUNT(*), 1) AS aov
FROM order_info;
```

错在哪：算出 **73.5 元**，比正确值 95.1 **低 21.6 元（-22.7%）**。3 张退款单、2 张取消单进了分母却几乎不进分子，五个"零金额分母"把客单价砸出深坑。退款处理要么"分子分母同剔"（本关口径），要么"分子分母同留"（并注明含退款），最怕只剔一头。

**错误写法二：报表 B（原价冒充实付）**

```sql
SELECT ROUND(SUM(goods_amount) / COUNT(*), 1) AS aov
FROM order_info;
```

错在哪：算出 **99.6 元**，比正确值 95.1 **虚高 4.5 元（+4.7%）**——优惠 274 元没扣，且 2 张未支付取消单（原价 132 元）计入分母。大促优惠力度越大，这个虚高越大；拿它去对毛利，财务对账永远差一截。

## 六、【侦探办案笔记】

### 本关指标口径总结

- 客单价铁律：**分子分母同一批订单**——`WHERE order_status='paid'` 必须同时罩住分子和分母。
- 实付口径（用户视角）与原价/GMV 口径（商家视角）是两个数，报表上各标各的名，优惠越大差距越大。
- 拆单会稀释订单口径的客单价；看用户钱包用"人均实付"，看购物意图用"主子单合并口径"。
- 退款单的处理方式（同剔/同留）要写进口径文档，最怕只剔一头。

### 业务方对齐口径的标准提问话术

1. "这个客单价是**实付口径还是原价口径**？优惠扣不扣？"
2. "**退款单算不算**？是分子分母同剔，还是同留？"
3. "满减**拆单**怎么处理？要不要补一个人均实付的口径？"

### 同类异常排查的通用方法论

"一个指标两个数"类案件（财务对账型）三步走：

1. **把两份 SQL 并排复现**——先确定它们各自算的是什么，再谈谁对谁错；
2. **按状态/类型拆分布**：`GROUP BY order_status` 把退款、取消的"单数 vs 金额"摆上台面；
3. **给出双口径结论**：一个标准口径给老板，一个辅助口径（人均/合并）给运营，附一句"两者差在哪"。
